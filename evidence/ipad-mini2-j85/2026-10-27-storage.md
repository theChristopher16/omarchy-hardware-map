# iPad mini 2 J85 RAM-boot storage inventory

This owner-run observation concerns one iPad mini 2 Wi-Fi (A1489/J85) on an
experimental runtime9 Linux RAM boot on 27 October 2026. The [draft bring-up
report](https://github.com/OrchardLinux/hardware/pull/5) records the broader
boot and hardware context.

A read-only Linux block-device inventory on the same RAM boot listed only
empty loop, network-block and zram devices. The root filesystem was rootfs;
no internal physical block device appeared in that inventory. No block
device was opened, no filesystem was mounted and no storage or bootloader
was written for this observation.

This means the running kernel did not expose a usable internal disk for an
installation at that moment. It does not prove the physical storage absent or
that another kernel could not support it. The [Hoolock A7 feature
matrix](https://github.com/HoolockLinux/docs/blob/master/features/A7.md)
lists internal storage as work in progress. A supported controller, device
verification and a recovery plan are needed before considering installation.
The existing external-root server was not restarted for this observation.

A subsequent local analysis of the recovered, fingerprinted J85 firmware found separate management paths for hello, power acknowledgments and endpoint enumeration. A host-only decoder of selected dispatch fields passed source-anchor and synthetic boundary checks. This does not establish mailbox framing, controller ownership, disk geometry, a usable block driver or a safe initialization sequence; no controller command was sent.

On 29 October 2026 UTC, a later runtime9 RAM boot again showed no internal physical block device: the partition list was empty, and the visible loop, network-block and zram entries reported zero sectors. The root remained RAM-backed. This was a read-only inventory; no block device was opened, mounted or changed. The finding describes that boot and does not establish that the hardware is absent.

A public, experimental [Hoolock ANS1 storage binding](https://github.com/HoolockLinux/linux/blob/ed8528f482a526371e59711645794c91fafb2b42/Documentation/devicetree/bindings/block/apple%2Cs5l8960x-ans.yaml) names an A7-compatible controller, but that is not a demonstrated J85 storage driver. Its accompanying [ASP driver source](https://github.com/HoolockLinux/linux/blob/ed8528f482a526371e59711645794c91fafb2b42/drivers/block/asp.c#L806-L824) attempts to enable writes during successful initialization before disks are registered. It was not loaded for this inventory and must not be treated as a read-only J85 test. Controller ownership, safe recovery and usable storage remain unverified.

## Public ANS1 dependencies and disabled-probe research

The public Hoolock ANS1 branch also includes an [RTKit interface](https://github.com/HoolockLinux/linux/blob/ed8528f482a526371e59711645794c91fafb2b42/include/linux/soc/apple/rtkit.h#L39-L70)
and an [AKF mailbox implementation](https://github.com/HoolockLinux/linux/blob/ed8528f482a526371e59711645794c91fafb2b42/drivers/soc/apple/mailbox.c#L367-L431).
A source comparison found RTKit callback and protocol-interface differences
from an [earlier public base](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/include/linux/soc/apple/rtkit.h);
copying the storage driver alone does not establish compatibility with other
kernel consumers. The mailbox provider's own probe maps registers, requests
interrupts and writes control registers, so disabling the storage probe alone
does not make an enabled mailbox provider passive.

A separate source-only storage candidate unconditionally refuses its probe.
It was independently reviewed and exercised with synthetic host fixtures;
it was not built as a kernel module, loaded or tested on the iPad. The public
source and disabled candidate do not establish compatible J85 integration,
internal-disk discovery, persistence or safe native storage. No physical
storage operation is claimed.

No recovered firmware, calibration, private logs, credentials, network
addresses or personal device identifiers are included here.


## Related public hardware results

The experimental Hoolock ANS1 branch's [J85 device-tree include chain](https://github.com/HoolockLinux/linux/blob/ed8528f482a526371e59711645794c91fafb2b42/arch/arm64/boot/dts/apple/s5l8960x-common.dtsi#L39-L56) enables an ANS node and references a firmware region that the loader must fill. This is source configuration, not proof that the controller has been initialized or storage read on J85.

An [A8X tester](https://github.com/HoolockLinux/docs/issues/19) reported creating and mounting an ext4 partition read/write with the experimental driver, followed by a journal abort during forced reboot. The report does not demonstrate clean unmount or durable write/readback. Separately, an [iPad Air 2 J81 developer](https://github.com/mattonik/ipad-nixos/blob/5915c17d993b38e8e9655c34e97b3796124f9f37/docs/plans/2026-09-13-j81-ans1-observation-only.md) reported ten read-only Linux namespaces and one 4 KiB read with the bytes discarded. Neither is a J85 test or evidence that this iPad is ready for internal installation.


## Offline ANS1 object compile

A source candidate derived from the public ANS1 branch was compiled offline as one AArch64 relocatable object using that source tree's ARM64 default configuration with selected ANS1 options. Its device probe was deliberately disabled; independent static inspection confirmed that the compiled probe returns `-ENODEV`. The compile reported two unused-function warnings.

This is not a linked kernel module or the iPad's verified kernel configuration. It does not demonstrate controller initialization, a usable block device, safe reads or writes, or an internal installation. The object was not loaded on the iPad, and no storage hardware was accessed for this build.
